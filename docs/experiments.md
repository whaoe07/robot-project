## 实验 0：静态抓取基线（ROS2 闭环）

**目的**：验证 ACT 策略在 ROS2 架构下的闭环成功率。

**设置**：方块固定 (0.55, 0)，无延迟、无抖动。

**结果**：50 次闭环评估，成功率 **84%**（判据：结束时方块仍被夹持在 init_z + 4cm 以上）。

**结论**：ROS2 改造后策略性能与单脚本评估一致，说明封装未引入退化。

## 实验 1：时延对静态抓取的影响

**目的**：测量控制链路延迟对抓取成功率的影响。

**设置**：在 `policy_node → sim_node` 之间插入 C++ `latency_node`，仅延迟 `/joint_command`。

| 延迟 | 抖动 | 丢包 | 次数 | 成功率 | 平均最终高度 |
|---|---|---|---|---|---|
| 0ms | 0 | 0 | 3 | 100% | 0.495 |
| 200ms | 0 | 0 | 3 | 100% | 0.497 |
| 500ms | 0 | 0 | 3 | 100% | 0.497 |
| 1000ms | 0 | 0 | 3 | 100% | 0.498 |
| 1000ms | ±100ms | 0 | 3 | 100% | 0.500 |
| 1000ms | 0 | 20% | 3 | 100% | 0.499 |

**结论（负结果，但有价值）**：

恒定延迟对准静态抓取任务**没有影响**，即使 1000ms + 20% 丢包。

**原因分析**：

策略输出的是**目标关节角序列**。恒定延迟只是让整个序列整体平移 1 秒，顺序和内容不变，机械臂最终仍会走完同一轨迹并抓住方块。

**这个结论说明**：延迟的破坏性取决于任务的动态性，而不是延迟本身。准静态任务对延迟几乎免疫；动态任务（追踪移动目标）则敏感。

**验证方式**：改为动态任务（见实验 3）。

## 实验 2：传送带速度对抓取的影响（设计缺陷，结论作废）

**目的**：找到系统能处理的最大传送带速度。

**设置**：方块起点 x=0.45（训练分布边缘），速度 0 / 0.001 / 0.003 / 0.005 / 0.007 / 0.010 m/s。

**结果**：

| 速度 | 成功率 |
|---|---|
| 0 | 80% |
| 0.001 | 0% |
| 0.003 | 100% |
| 0.005 | 0% |
| 0.007 | 0% |
| 0.010 | 0% |

**结论：本实验作废。** 非单调曲线（0.001 比 0.003 差）说明存在混淆变量。

**失败原因**：

所有组起点相同（0.45），但不同速度下**抓取时刻的方块位置不同**。位置效应（0.45 是分布边缘，难抓）压过了速度效应，导致曲线非单调。

**教训**：控制变量时，要考虑"间接效应"——改变速度会同时改变位置，必须一并控制或随机化。

## 实验 3：方块尺寸泛化

**目的**：测量策略对未见过尺寸的泛化能力（域泛化）。

**设置**：

- 起点固定 x=0.55（训练分布中心）
- 传送带速度固定 0.003 m/s
- 延迟 0
- 边长 4 / 5 / 6 / 7 cm（训练只见 5cm）
- 成功判据：抬离桌面 4cm（随尺寸动态调整）

**结果**：

| 边长 | 次数 | 成功率 | 平均最终高度 | 抓后最低 |
|---|---|---|---|---|
| 4cm | 5 | **60%** | 0.484 | 0.468 |
| 5cm | 5 | **80%** | 0.480 | 0.474 |
| 6cm | 5 | **0%** | 0.430 | 0.430 |
| 7cm | 5 | **0%** | 0.435 | 0.435 |

**结论**：

1. **零泛化**：训练分布（5cm）之外，尺寸稍大（6cm）即完全失效。
2. **系统有固有不确定性**：5cm 组仅 80%，与静态抓取实验的 84% 一致，说明约 20% 的失败来自系统本身的随机性（非尺寸因素）。
3. **小尺寸有部分容忍**：4cm 达 60%，成功案例中方块被顶在指尖（final_z=0.54，高于 5cm 的 0.49）。
4. **大尺寸完全失效**：6cm 出现"抬起后掉落"（max_z 0.459–0.487），夹持不稳；7cm 几乎没动（max_z 0.435–0.444），夹爪张开余量不足。

**原因分析**：

策略记忆的是**针对 5cm 方块的具体动作序列**（下降高度、手指闭合角度），而非通用抓取技能。6cm 方块表面高 5mm，策略按 5cm 的高度下降，手指压在方块顶部或抓空。

**改进方向**：域随机化（训练数据覆盖 4–7cm），或几何感知输入（输入方块尺寸估计）。

## 技术问题记录

### 问题 1：MuJoCo 运行时改 geom_size 导致物理爆炸

**现象**：改 `model.geom_size` 后，6cm/7cm 方块的 `max_z` 出现 111、131、779、2173 等异常值。

**原因**：MuJoCo 的几何尺寸是编译期参数。运行时改只影响部分数据结构，惯性张量仍是旧尺寸计算的，碰撞体未同步，导致穿模后被弹飞。

**解决**：读取原 XML，按目标尺寸替换 `size` / `mass` / `pos` 后写入新 XML，再 `from_xml_path` 加载。

**教训**：`model.*` 大多是编译产物，运行时修改要么无效要么产生自相矛盾。正确做法是改 XML 重新编译。

### 问题 2：bash 脚本参数解析错误

**现象**：`IFS=',' read -r a b c <<< "$s"` 在 WSL 环境中解析出 `1000`、`24` 等错误值。

**解决**：改用 Python 重写实验脚本，用元组和 `csv` 模块，彻底避开 shell 的 IFS/编码问题。

### 问题 3：QoS 不匹配导致"发了没反应"

**现象**：`command_node` 用 best-effort 发布，`sim_node` 用 reliable 订阅，`cmds` 恒为 0，程序不报错。

**解决**：双方日志都有 WARN 提示 `incompatible QoS`；排查命令 `ros2 topic info <topic> --verbose`。

**教训**：ROS2 里"发了没反应"第一件事查 QoS。

### 问题 4：代码没同步到服务器导致实验作废

**现象**：本地改了 `act_model.py`，未 scp 到服务器，重训结果与上次完全相同。

**解决**：建立"改代码 → py_compile → scp → grep 确认 → 运行"的流程，grep 用具体标志（如 `AdaptiveAvgPool2d(4)`）。

### 问题 5：C++ 代码改动未编译

**现象**：改了 `command_node.cpp` 但 `colcon build` 只用 0.24 秒，日志仍显示旧值。

**原因**：源文件未保存，或编译缓存认为无变化。

**教训**：**编译时间异常短 = 没有真正编译**。改完先用 `grep` 确认文件内容。
